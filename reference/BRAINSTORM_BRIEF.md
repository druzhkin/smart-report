# Smart Report — Бриф для брейншторма с ИИ

Документ для загрузки в любую ИИ-модель (ChatGPT / Claude / Gemini / Perplexity), чтобы провести брейншторм по архитектуре и продуктовому видению проекта. Содержит: что есть сейчас, куда целимся, и ключевые ограничения.

---

## 1. Что это за проект

**Smart Report** — это не ещё один «саммаризатор поисковой выдачи». Это попытка построить **«Perplexity на стероидах»**: полноценный аналитический движок, который ведёт себя как настоящий исследователь-человек, а не как LLM с подключённым веб-поиском.

### Ключевое отличие от Perplexity / ChatGPT Search / Gemini Deep Research

Perplexity и аналоги работают по схеме:

> запрос → поиск → прочитал топ-10 → суммаризировал → отдал плоский ответ.

Smart Report должен работать по схеме **настоящего аналитика**:

1. **Понимает задачу по-настоящему** — не ключевые слова, а цель пользователя, контекст, ограничения, стейкхолдеров, на какое решение влияет ответ.
2. **Строит исследовательский план** — какие ветки гипотез надо проверить, в каком порядке, какие источники для каждой ветки авторитетны.
3. **Идёт по огромному количеству источников** — не 10 ссылок из Google, а десятки-сотни: отраслевые базы, регуляторы, академия, отчёты консалтинга, финансовая отчётность, патенты, статистика, интервью, форумы практиков, корпоративные блоги, специализированные БД.
4. **Задаёт себе вопросы по ходу** — «а что я упускаю?», «это единичный кейс или тренд?», «кто бы сказал обратное и почему?», «какие цифры не бьются?», «какие допущения я делаю неявно?».
5. **Ставит гипотезы и проверяет их** — не просто пересказывает источники, а формулирует утверждения и ищет подтверждения/опровержения.
6. **Видит пробелы и закрывает их** — если данных не хватает для вывода, идёт искать ещё, а не «галлюцинирует вежливо».
7. **Синтезирует, а не пересказывает** — находит паттерны между источниками, противоречия, неявные следствия.
8. **Мотивирован на глубину** — ведёт себя как человек, которому реально интересно разобраться, а не как работник, отрабатывающий минимум. Формальный плоский ответ — это провал, не успех.

По сути — **почти научный аналитик** по вайбу: любопытный, въедливый, не удовлетворяется первым правдоподобным ответом.

### Функциональные требования

- **Универсальность по доменам**. Должен работать на любой теме: медтех, FMCG, LLM-инфраструктура, B2B SaaS, регуляторика, венчур, HR, наука, промышленность. Без хардкода под конкретные индустрии.
- **Разные уровни глубины** — тиры исследования:
  - `light` — быстрый ответ, минимум источников, дешевле $0.5.
  - `standard` — стандартный аналитический отчёт.
  - `deep` — глубокое исследование с разветвлённым планом.
  - `exhaustive` — максимум, «как будто неделя работы аналитика»; дорогой, но конечный по стоимости.
- **Языки** — как минимум русский и английский, с корректным деловым форматированием в обоих.
- **Форматы артефактов**:
  - **Word / DOCX** — деловое форматирование, подходящее для отправки клиенту/боссу: типографика, нумерация, таблицы, сноски, оглавление.
  - **PDF / HTML / Markdown** — синхронизированные версии того же отчёта.
  - **Презентации** — Gamma-style или PowerPoint, с визуальным дизайном, а не дампом буллетов.
  - **Инфографика / визуализации** — графики, диаграммы, схемы, которые реально помогают понять, а не «заполняют слайд».
- **Доказательность (evidence-first)** — каждое содержательное утверждение прицеплено к источнику; цифры прослеживаются до первичного документа; противоречия между источниками явно отмечаются, а не замазываются.
- **Экономика** — юнит-экономика должна сходиться. Даже `exhaustive` должен иметь потолок стоимости и не «разоряться» на случайном запросе. Бюджеты и модели (дорогие vs дешёвые) выбираются осознанно по стадиям пайплайна.

### Продуктовое позиционирование

Пользователи — те, кому сейчас недостаточно Perplexity/ChatGPT, но кто не может позволить себе неделю работы внешнего консалтинга. Продакт-менеджеры, стратеги, венчурные аналитики, основатели, консультанты, исследователи рынков. Ценность — получить за минуты/часы то, что обычно требует дней и тысяч долларов, **и при этом не получить плоский мусор**.

## 2. Текущее состояние (2026-04-14)

Честная картина, без маркетинга.

### Стек

- **Backend**: Python 3.12, FastAPI, LangGraph, OpenRouter (роутинг моделей), PostgreSQL, Redis, опционально RAGFlow.
- **Frontend**: Next.js 16, React 19, Tailwind v4, shadcn/ui, Framer Motion, Recharts.
- **Research sources**: Perplexity (основной), задумана интеграция с GPT-Researcher, RAGFlow для пользовательских материалов.
- **Рендер**: python-docx, HTML→PDF, Gamma API для слайдов.
- **Деплой**: Railway, один сервис с фронтом+бэком.

### Архитектура (фактическая, не желаемая)

Сейчас в репозитории **сосуществуют два движка**:

1. **v1 (legacy)** — `backend/pipeline/graph.py` + `backend/agents/*.py`. Классический LangGraph-пайплайн из 8 стадий: intake → prompt_router → prompt_king → supervisor → research → reflect → render → qa. Каждая стадия — отдельный агент-обёртка вокруг LLM с системным промптом из `prompts/`.
2. **v2 (active)** — `backend/v2/pipeline.py`. Монолитный async-оркестратор (~13k строк в одном файле), который импортирует хелперы из v1 (`_research_single`, `_build_rich_docx`, рендерер) и запускает свой собственный цикл: intake → research plan → search → grounding → audit → render. v2 **не** использует граф v1, но сидит на его коде.
3. **dual_engine** (`backend/v2/dual_engine.py`) — гибрид для сравнений в евалах.

Ключевые v2-модули:

- `v2/intake.py` — парсинг запроса в `RequestSpec` + `DepthProfile` (тиры глубины, бюджеты).
- `v2/models.py` — pydantic-схемы всех артефактов (`AnalysisBrief`, `ResearchPlan`, `CoverageReport`, `AuditSummary`, `ReportType`, `RequestArchetype`).
- `v2/search.py` + `v2/source_registry.py` — внешний ресёрч, дедуп, скоринг источников.
- `v2/grounding.py` — извлечение числовых фактов, детекция противоречий, санитизация неподтверждённых цифр.
- `v2/quality.py` + `v2/audit.py` — release gate: аудит отчёта → `AuditSummary` → решение о публикации.
- `v2/materials.py` + `v2/repository.py` — загруженные пользователем материалы и персистентность артефактов под `reports/`.

Frontend: страницы `app/new/` (создать запрос), `app/reports/` (прогресс + вьюер), `app/library/`, `app/settings/`. Поток: `lib/api.ts` → `hooks/useSSE.ts` (SSE-события от бэкенда) → `components/ReportViewer.tsx`.

### Что работает

- Intake и построение `RequestSpec` / `DepthProfile`.
- SSE-стриминг прогресса в UI.
- Рендер DOCX с читаемым деловым форматированием.
- Пайплайн запускается end-to-end и выдаёт артефакты.
- Eval-харнесс (`scripts/run_golden_evals.py`, `benchmark_depth_costs.py`) работает и даёт честные цифры.

### Что сломано (подтверждено евалами 2026-04-14)

1. **Семантический ретривал ломается**. На запросе «Evaluate LLM observability platforms for an enterprise document workflow product» система притащила источники про прослеживаемость продуктов питания (FSMA 204, Trustwell Food LogiQ), медицинский ERP и отладку прошивок. Только ~2 из 15 источников по теме.
2. **Template leakage**. Все клеймы в примере начинаются с f-string-шаблона `"On '{question}', the merged engine output points to this pattern: {snippet}"` — синтез клеймов не происходит, система просто оборачивает сырые сниппеты Perplexity.
3. **Хардкод уверенности**. Каждый клейм получает `confidence: 0.82` и `recommendation_safe: true` независимо от содержания.
4. **Release gate блокирует всё**. `audit_summary.json` стабильно показывает `release_status: blocked` с «Broken footnote-style citations» и «Topic alignment too weak: 67.8/100». На всех четырёх тирах (light/standard/deep/exhaustive, $0.29–$3.18) отчёт помечается как непригодный к выпуску.
5. **«Dual engine» — маркетинг**. В сэмплах видно `GPT-Researcher disabled in settings`. Реально работает только Perplexity.
6. **Монолит и связанность**. `v2/pipeline.py` ~13k строк, импортирует код v1. Это не чистая переделка, а надстройка над старым движком.
7. **Reference-пак как чит**. `v2/reference_data.py` + shortcut в pipeline позволяют запросам, похожим на заготовленные паттерны, вообще обходить живой ресёрч и возвращать пред-замороженный контент — это искажает евалы и демо.
8. **Quality loop без рук**. `quality.py` умеет переписывать прозу, но не умеет заказывать **новые** факты/источники. Поэтому пробелы в данных никогда не закрываются — только переформулируются.
9. **Depth-профили не форсятся**. `intake.py` объявляет, что DEEP = 5 веток × 20 источников, но пайплайн эту цель не энфорсит.
10. **Мёртвый код**. В `v2/intake.py:991` сидит `if False:` блок (заготовка под Moscow market entry).

### Исходный замысел

Был зафиксирован в `NEW_SMART_REPORT_V2_TZ.md` (44 KB в корне) — описание evidence-first архитектуры, от которой текущая реализация заметно отклонилась. Есть также `SMART_REPORT_V3_REBUILD_BRIEF.md` с бриф-заданием на ребилд.

### Вывод по текущему состоянию

Текущий v2 — это **не спасаемая база**. Артефакты можно читать как требования («что должно было быть»), но строить на этом коде дальше — значит воспроизводить уже известные дефекты. Нужна архитектурная переработка с опорой на уроки этой попытки.

## 3. Цели (куда целимся)

### Продуктовая цель

Сделать инструмент, который на ответе на сложный аналитический вопрос **объективно превосходит** Perplexity Deep Research, ChatGPT Deep Research и Gemini Deep Research по:

- **глубине** (сколько релевантных источников реально прочитано и использовано);
- **точности цифр** (каждая цифра прослеживается до первичного источника, противоречия явно отмечены);
- **структуре и формату** (выходит готовый к отправке клиенту документ, а не «текст в чате»);
- **честности** (если данных нет — сказано «нет данных», а не сгаллюцинировано);
- **универсальности** (работает на незнакомом домене без предварительной настройки).

### Архитектурные цели

1. **Evidence-first, а не narrative-first**. Сначала собираем проверенные факты → из них синтезируем нарратив. Не наоборот.
2. **Исследовательский цикл с обратной связью**. Система должна уметь: прочитать → заметить пробел → сформулировать уточняющий вопрос → пойти искать ещё → интегрировать новое → перепроверить вывод. Это не линейный пайплайн, это петля.
3. **Мотивация на глубину, встроенная в промпты и контроль**. Критик-агент, который оценивает «выглядит ли это как работа заинтересованного аналитика или как отписка», и возвращает в цикл, если отписка.
4. **Реальный зоопарк источников**. Не только Perplexity API. Специализированные коннекторы: академия (arXiv, Semantic Scholar), регуляторы, статистика, финансовые фильтры (SEC, ЕГРЮЛ), патенты, отраслевые БД, RAGFlow над загруженными материалами пользователя.
5. **Гипотезы как first-class objects**. Система явно формулирует H1, H2, H3, ведёт по каждой доказательную базу, отмечает «подтверждено / опровергнуто / недостаточно данных».
6. **Release gate, который помогает, а не блокирует всё подряд**. Аудит должен давать конкретные действия («добавь источник по X», «проверь цифру Y»), а не ставить красный свет без руководства к действию.
7. **Экономика по стадиям**. Дорогие модели — только там, где они окупаются (синтез, критика, финальный рендер). Дешёвые — на рутине (дедуп, классификация, извлечение фактов). Жёсткий потолок на тир.
8. **Форматы как first-class output**. Word/PDF/слайды — это не «postprocess», а проектируемые артефакты со своими контрактами (структура, визуал, длина, тон).

### Не-цели

- Чат-интерфейс общего назначения (это не ChatGPT).
- Реал-тайм-ответы (< 30 сек). Deep research по определению занимает минуты.
- Домен-специфичные «пакеты» (медицинский режим, юридический режим). Универсальность — принципиальная установка.
- Собственная модель. Всё через OpenRouter/провайдеров.

## 4. Ключевые ограничения и контекст

- **Бюджет инфраструктуры** — проект single-developer-scale, деплой на Railway, без собственного кластера.
- **Бюджет запроса** — пользователь не должен платить больше, чем получает ценности. `exhaustive` — условно $3–5, а не $50.
- **Язык пользователя** — владелец проекта говорит по-русски, но продукт должен быть многоязычным.
- **Команда** — разработку ведёт владелец + ИИ-агенты. Сложность архитектуры должна быть посильной для такой модели.
- **Опыт прошлых попыток** — три ребилда v2 уже не дали работающий продукт. Следующая итерация должна учитывать, **почему** предыдущие не взлетели (монолит, отсутствие обратной связи в цикле, хардкод, release gate без рук).

## 5. Вопросы для брейншторма

Что можно обсудить с ИИ-собеседником:

1. **Архитектура исследовательского цикла.** Как устроить петлю «план → поиск → синтез → критика → новые вопросы → поиск» так, чтобы она сходилась, а не зацикливалась? Как задать критерий «достаточно глубоко, можно останавливаться»?
2. **Гипотезы как объекты.** Как формализовать H/evidence/verdict так, чтобы это было полезно и для LLM-агента, и для пользователя в UI?
3. **Расширение источников.** Какие коннекторы дают наибольший прирост качества на универсальных запросах? Как вести «реестр источников» по авторитетности и доменам?
4. **Экономика.** Как распределить бюджет тира по стадиям, чтобы дорогие модели работали только там, где это окупается?
5. **Промпты мотивации.** Какие формулировки в system prompt реально заставляют LLM вести себя как въедливый аналитик, а не как вежливый помощник?
6. **Release gate, который учит.** Как сделать, чтобы аудит не просто блокировал, а возвращал конкретные задачи в цикл?
7. **Формат как контракт.** Как спроектировать DOCX/слайды/инфографику так, чтобы на выходе был артефакт уровня консалтинга, а не «LLM-сгенерированный текст»?
8. **Evals.** Как мерить глубину и честность, а не только «похоже на отчёт»? Какие golden-queries честно покрывают универсальность?
9. **Уроки из провалов.** Что именно в текущем v2 было архитектурной ошибкой, а что — недоработкой? Что надо выбросить, что сохранить?
10. **Дифференциация.** Какие 2–3 свойства продукта надо довести до уровня, на котором Perplexity принципиально не сможет догнать без радикальной переделки своей архитектуры?
